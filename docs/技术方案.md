> 依据：`Web Game Hub 设计文档.md`（以下简称「设计文档」）
> 状态：方案评审稿 v1
> 范围：仅方案，不含代码实现

## 1. 需求理解

### 1.1 产品定义

无安装的 Web 游戏平台：打开网页 → 选游戏 → 建房/进房 → 扫码 → 手机变手柄 → LAN/WebRTC 联机；游戏运行在房主设备，存档在房主浏览器。

### 1.2 三条不可破坏的约束（设计文档核心原则）

| # | 约束 | 含义 |
|---|---|---|
| 1 | Cloudflare Control Only | Worker 只做房间、身份、信令、心跳；不跑游戏、不转发游戏数据、不存 Save |
| 2 | Local First | 游戏运行、状态、Save State 全在房主浏览器 IndexedDB |
| 3 | P2P First | 实时数据优先 LAN → WebRTC；Worker 不参与正常游戏数据 |

### 1.3 MVP 边界（设计文档 §43 / §51）

**做**：HTML5 游戏、建房/进房、QR 邀请、WebRTC、触屏控制器、Gamepad、IndexedDB 存档。

**不做**：云存档、视频转发、游戏状态上传、Host Migration、账号体系、排行榜、原生 App、模拟器（第二阶段）、LAN 专用协议（见 D2）。

## 2. 已确认决策（ADR）

方案编制期间与需求方确认的 8 项决策。**未列入本表的内容一律标为「开放问题」，不作假设。**

| ID | 决策 | 选择 | 理由 |
|---|---|---|---|
| D1 | 信令通道 | **客户端 HTTP 轮询**（握手期 `GET /signal?after=N`，约 1s 间隔） | Worker 无状态、无法主动推送；WebRTC 连通后信令通道仅剩握手几秒在用，轮询成本近乎为零、无新增组件。延迟 0–1s 对 Offer/Answer/ICE trickle 可接受 |
| D2 | LAN 实现 | **就用 WebRTC 本地候选**（host/mDNS candidate 同网段直连） | 浏览器拿不到 SSID/IP，无法做独立 LAN 发现；「LAN 模式」= 优先选本地候选 + 热点引导文案 |
| D3 | 客户端形态 | **两种都要**：`player`（本地跑游戏并渲染）与 `controller`（纯手柄页） | 设计文档 §16 与 §18 分别描述，同一加入流程分 profile 实现 |
| D4 | 多人拓扑 | **MVP 固定 2 人，仅 Host↔Client** | 对应 manifest `players: 2` 与 §48 图示；3+ 人留到扩展期 |
| D5 | 工程栈 | **Vite + TypeScript + pnpm workspace**，不引 UI 框架，游戏本体原生 Canvas | 保留设计文档「原生 TS/JS」定位，同时获得构建、类型检查、monorepo 包复用 |
| D6 | 本阶段交付物 | **仅方案文档** | — |
| D7 | MVP 演示游戏 | **Snake 双人对战** | 状态小、确定性易保证，适合验证输入同步 |
| D8 | 信令升级路径 | MVP 用轮询；`SignalingChannel` 接口按可替换设计，**后续可无损切换 DO+WebSocket** | 不锁死，不提前支付复杂度 |

### 2.1 对设计文档的增补（D1 引入）

设计文档 §31 的 API 列表没有可轮询的信令读取端点。本方案增补：

```text
GET /api/rooms/:id/sync?after=<cursor>   # 轮询：一次性返回 房间状态 + 信令消息
```

并在 D1 数据模型中新增 `signals` 表（见 §7.3）。其余 API 与设计文档 §31–§34 一致。

## 3. 总体架构

### 3.1 三个平面（沿用设计文档 §3）

```text
┌─────────────────────────────────────────────────────────┐
│ Control Plane   Worker + D1                             │
│   房间状态机 / Token / 心跳 / 信令中转(轮询)             │
└──────────────────────────┬──────────────────────────────┘
                           │ 仅握手期
┌──────────────────────────▼──────────────────────────────┐
│ Realtime Plane   WebRTC DataChannel（本地候选即 LAN）    │
│   InputEvent / Frame / Sync / 控制消息                  │
└──────────────────────────┬──────────────────────────────┘
                           │
┌──────────────────────────▼──────────────────────────────┐
│ Local Game Plane   Browser + IndexedDB                  │
│   游戏运行 / 渲染 / 存档 / 输入采集                      │
└─────────────────────────────────────────────────────────┘
```

### 3.2 运行时角色

| 角色 | 职责 | 形态 |
|---|---|---|
| **Host** | 跑完整游戏、权威帧时钟、存档、心跳、建房 | 房主浏览器 |
| **Player / `player` profile** | 加载同一份游戏构建，本地渲染，收发输入 | 玩家浏览器（手机/PC） |
| **Player / `controller` profile** | 只发输入，不跑游戏；可收少量展示信息（比分/状态） | 玩家浏览器（手机） |
| **Worker** | 房间、Token、心跳、信令中转 | Cloudflare |

Host 与 Client 在**同一房间内互为对端**，2 人拓扑下只有 1 条 DataChannel（D4）。

| `input` | 三类输入源统一为 `InputEvent`，按游戏 manifest 做 Mapping | `InputSource` | 新输入源 = 新实现（含远程手机手柄页） |

| `apps/web` | 四个入口页，共享同一 session | 路由见 §5 | 页面独立演进 |
| `worker` | 房间状态机、Token 签发校验、信令中转、心跳判定 | HTTP API 见 §7 | D1 表只增不改 |

## 5. 前端页面与流程

### 5.1 路由

| 路由 | 页面 | 说明 |
|---|---|---|
| `/` | Hub | 游戏列表（读 manifest） |
| `/game/:gameId` | Game | 单机启动 / 「创建房间」按钮 |
| `/join/:roomId` | Join | 扫码落地页，填昵称 → 进房 |
| `/room/:roomId` | Room | 房主页：QR、玩家列表、开局/关闭 |
| `/controller/:roomId` | Controller | 纯手柄页（`controller` profile） |

### 5.2 建房 → 扫码 → 联机时序（含轮询）

```text
Host                         Worker                        Client
  │ POST /rooms {gameId,mode} │                              │
  │──────────────────────────►│ D1: INSERT rooms             │
  │◄── roomId + hostToken ────│                              │
  │ 生成 joinUrl / QR          │                              │
  │                            │        POST /rooms/:id/join │
  │                            │◄────────────────────────────│ (joinToken)
  │                            │──── playerToken ───────────►│
  │ GET /sync?after=0 (host)   │                              │
  │──────────────────────────►│◄────── GET /sync?after=0 ────│  ← 双方各 ~1s 轮询
  │◄─ {joined: player} ───────│                              │
  │ createOffer()              │                              │
  │ POST /signal {offer} ─────►│ 落 D1 signals 表             │
  │                            │─────── 下轮 GET /sync ──────►│
  │                            │◄────── POST /signal answer ──│
  │◄── GET /sync 返回 answer ──│                              │
  │ ICE candidates（同样走 signal，trickle）                   │
  │                            │                              │
  │◄══════════ RTCDataChannel 建立（同网段即走本地候选）══════►│
  │                            │                              │
  │ POST /heartbeat 每 15s ───►│                              │
  │ （握手完成后双方停止 /sync 轮询，仅保留心跳）                 │
```

**轮询纪律**（控制 D1 免费额度 500 万行读/天）：
- 仅在「等待加入」与「WebRTC 握手」阶段轮询，间隔 1s（带 jitter）。
- 连通后停止轮询，改为按需 `GET /rooms/:id`（客户端每 10s 查一次房间状态，用于 HOST_LOST 感知）。
- 每次轮询顺带清理该房间 5 分钟前的 signals 行。

### 5.3 断线处理

| 场景 | 行为（第一版，不做 Host Migration） |
|---|---|
| Host 心跳超时（>45s，3×15s） | Worker 置 `HOST_LOST`；Client 轮询到后界面暂停并提示「等待房主」 |
| Host 恢复 | 心跳恢复 → `PLAYING`；Host 重新 createOffer 建链（信令通道复用） |
| DataChannel 断 | 双方回退到 `/sync` 轮询重新握手；游戏暂停 |
| Host 关页 | 房间最终 `EXPIRED`；IndexedDB 存档保留，下次打开继续 |

## 6. 核心协议（`packages/protocol`）

### 6.1 Game Manifest（扩展自设计文档 §4.3）

```jsonc
{
  "id": "snake",
  "name": "Snake",
  "version": "1.0.0",
  "type": "html",                  // html | emulator(预留)
  "players": 2,                    // MVP 固定 2 (D4)
  "controller": { "type": "generic" },
  "multiplayer": { "supported": true, "sync": "input" },
  "entry": "/games/snake/index.html",
  "tickRate": 20,                  // 权威帧率（Snake 每秒逻辑帧）
  "inputDelayFrames": 2,           // 输入延迟帧数
  "stateHashInterval": 0           // 0=暂不校验；>0 表示每 N 帧比对哈希
}
```

`type: "emulator"` 与 `engine`/`core` 字段为第二阶段预留，解析器遇到未知字段**忽略不报错**（前向兼容）。

### 6.2 InputEvent（设计文档 §14）

```ts
type Button = 'UP'|'DOWN'|'LEFT'|'RIGHT'|'A'|'B'|'X'|'Y'|'L'|'R'|'START'|'SELECT';

interface InputEvent {
  v: 1;
  type: 'input';
  frame: number;      // 目标应用帧（Host 权威时钟）
  player: 1 | 2;
  button: Button;
  pressed: boolean;
}
```

按键集合固定，具体映射由各游戏的 Controller Mapping 决定（游戏 manifest 可覆盖）。

### 6.3 同步消息（设计文档 §21，第一阶段 InputSync）

```ts
type SyncMessage =
  | { v:1; type:'input';      frame:number; player:1|2; input:Partial<Record<Button,boolean>> }
  | { v:1; type:'frame';      frame:number; seed:number }            // 帧基准（开局一次）
  | { v:1; type:'state';      frame:number; payload:Uint8Array }     // 预留: resync 快照
  | { v:1; type:'hash';       frame:number; hash:string }            // 预留: 去同步检测
  | { v:1; type:'control';    event:'pause'|'resume'|'end' };
```

### 6.4 信令消息（走 HTTP 轮询，D1 `signals` 表）

```ts
type SignalMessage =
  | { kind:'offer';  sdp:string }
  | { kind:'answer'; sdp:string }
  | { kind:'ice';    candidate:object }
  | { kind:'bye';    reason:string };
```

## 7. Control Plane（Worker）

### 7.1 房间状态机（设计文档 §6/§7）

```text
CREATED → WAITING → PLAYING ⇄ PAUSED
              │        │        │
              │        └──► HOST_LOST ──► PLAYING（心跳恢复）
              │                 │
              └──── CLOSED ◄────┘（主动关闭）
                        EXPIRED（HOST_LOST 超时）
```

状态迁移只由 Worker 执行；客户端只能通过 API 触发迁移，不能直接写状态。

### 7.2 API（与设计文档 §31 一致 + D1 增补）

| Method | Path | 鉴权 | 说明 |
|---|---|---|---|
| POST | `/api/rooms` | hostToken（返回） | 建房，返回 `roomId / joinUrl / hostToken / expiresAt` |
| POST | `/api/rooms/:id/join` | joinToken | 加入，返回 `playerToken`、`gameId`、`profile` |
| POST | `/api/rooms/:id/leave` | 各自 token | 主动离开 |
| POST | `/api/rooms/:id/heartbeat` | hostToken | 15s 一次，更新 `last_heartbeat` |
| GET | `/api/rooms/:id` | 任一 token | 截取房间状态（客户端 10s 轮询用） |
| **GET** | **`/api/rooms/:id/sync?after=N`** | 各自 token | **增补**：返回 `{status, since, signals[]}` |
| POST | `/api/rooms/:id/signal` | 各自 token | 写入一条信令（只允许写给对端） |
| DELETE | `/api/rooms/:id` | hostToken | 关闭房间 |

### 7.3 D1 数据模型（设计文档 §29 + 增补 `signals`）

```sql
CREATE TABLE rooms (
    id TEXT PRIMARY KEY,
    game_id TEXT NOT NULL,
    host_id TEXT NOT NULL,
    status TEXT NOT NULL,
    mode TEXT NOT NULL,
    created_at INTEGER NOT NULL,
    updated_at INTEGER NOT NULL,
    last_heartbeat INTEGER
);

CREATE TABLE players (
    id TEXT PRIMARY KEY,
    room_id TEXT NOT NULL,
    nickname TEXT,
    role TEXT NOT NULL,          -- host | player
    joined_at INTEGER NOT NULL,
    last_seen INTEGER
);

CREATE TABLE sessions (
    id TEXT PRIMARY KEY,
    room_id TEXT NOT NULL,
    token_hash TEXT NOT NULL,    -- 仅存哈希
    role TEXT NOT NULL,
    expires_at INTEGER NOT NULL,
    created_at INTEGER NOT NULL
);

-- 增补：信令队列（轮询读取，握手后清理）
CREATE TABLE signals (
    id INTEGER PRIMARY KEY AUTOINCREMENT,   -- 作为轮询游标
    room_id TEXT NOT NULL,
    from_role TEXT NOT NULL,     -- host | player
    to_role TEXT NOT NULL,
    payload TEXT NOT NULL,       -- SignalMessage JSON
    created_at INTEGER NOT NULL
);
CREATE INDEX idx_signals_room ON signals(room_id, id);
```

**D1 不存**（设计文档 §30）：Game Save、Save State、ROM、GameState、FrameBuffer、视频、输入历史。

### 7.4 Token 与权限（设计文档 §35–§37）

- `hostToken` 与 `joinToken` 分离，均随机生成、有过期时间、存哈希、可撤销。
- hostToken：建房/关房/心跳/重连/管理玩家。
- joinToken：查房/加入/建立连接。
- Room ID（如 `A8F3K9`）用于 URL 展示，鉴权一律走 Token，不信任路径参数。
- MVP 无账号体系（设计文档 §51），身份 = 浏览器 localStorage 中的匿名 UUID + 房间级 Token。

## 8. Realtime Plane

### 8.1 Transport 抽象（`packages/net`）

```ts
interface Transport {
  readonly kind: 'loopback' | 'webrtc';
  readonly state: 'connecting' | 'open' | 'closed';
  send(channel: 'input' | 'sync' | 'control', data: Uint8Array): void;
  on(channel: string, cb: (data: Uint8Array) => void): void;
  onStateChange(cb: (s: Transport['state']) => void): void;
  close(): void;
}
```

- `LoopbackTransport`：单机模式，输入直接回环给本地游戏 —— **让 M1 完全不依赖网络**。
- `WebRTCTransport`：MVP 唯一联网实现；`kind` 若经本地候选连通，UI 标注「LAN」（D2），代码路径不变。
- DataChannel 分三条：`input`（可靠有序，低延迟优先可设 `ordered:false`）、`sync`（状态/哈希）、`control`（暂停等）。第一版全部可靠有序，避免额外复杂度。

### 8.2 NAT 失败回退（开放问题 O1）

设计文档 §3.2 提到「必要时再考虑 Relay」。纯 STUN 在对称 NAT 下会失败。**MVP 是否内置 TURN 未确认**，暂定：失败时明确提示「无法直连」并给出热点引导（§10）。

### 8.3 同步引擎（`packages/core`，`InputSyncStrategy`）

**模型**：Host 是权威帧时钟；双端各跑一份确定性游戏逻辑，按相同帧应用相同输入。

```text
Client 本地输入 ──(frame = now + inputDelayFrames)──► Host
Host 本地输入 ──► Host 输入队列
Host 每帧 tick：
   1. 取出 frame == N 的所有输入（含双方）
   2. 应用到本地游戏 → 渲染
   3. 把 frame N 的「已采纳输入集合」广播给 Client
Client 收到后：
   在自己 frame N 应用同一集合 → 本地渲染
```

要点：
- **输入延迟 2 帧**换双向确定性，避免回滚（第一版不做 rollback，设计文档 §45 留到第三阶段）。
- 确定性要求（设计文档 §20）：游戏逻辑禁止 `Math.random()` 与浮点时间依赖，改用种子化 PRNG（开局随 `frame`/`seed` 消息下发）与整数/定点运算。**Snake 实现必须遵守该约定。**
- 去同步检测：`stateHashInterval > 0` 时每 N 帧互发 `hash`；不一致则 Host 发 `state` 快照强制对齐（Snake 状态极小，快照成本可忽略）。MVP 可先不启用，协议已预留。
- `controller` profile 不跑游戏，只发 `InputEvent`、可收 `control` 与轻量展示数据。

### 8.4 输入层（`packages/input`）

```text
TouchScreen ─┐
Gamepad API ─┼─► InputSource ─► InputEvent ─► Controller Mapping ─► Transport / 本地游戏
Keyboard ────┘
```

- Touch：虚拟方向键 + A/B/START/SELECT，按下即发、抬起即发（成对，防丢键）。
- Gamepad：`gamepadconnected` 事件 + `requestAnimationFrame` 轮询读取，标准化为平台 Button。
- Mapping 由游戏 manifest 覆盖，默认 generic。
- 压力：`pressed=false` 必须可靠送达，否则按键卡死；`control` 通道发送按键状态全量快照（每 500ms 一次）作为自愈机制。

## 9. Local Game Plane

### 9.1 IndexedDB（设计文档 §23–§24）

```text
WebGameHub
├── games            # 游戏元数据/缓存的 manifest
├── saves            # gameId + slot + data + updatedAt
├── emulator_states  # 第二阶段
├── settings         # 手柄映射、音量、昵称
└── local_rooms      # 最近的房间记录（重开恢复入口）
```

`saves.data` = `ArrayBuffer | Blob | JSON`。**存档只在房主浏览器，服务端无感知**（设计文档 §27）。

### 9.2 GameStorage API（设计文档 §25）

```ts
interface GameStorage {
  save(slot: string, data: ArrayBuffer | Blob | JSONValue): Promise<void>;
  load(slot: string): Promise<ArrayBuffer | Blob | JSONValue | null>;
  delete(slot: string): Promise<void>;
  list(): Promise<{ slot: string; updatedAt: number }[]>;
}
```

由 `game-sdk` 注入给游戏，游戏不感知 IndexedDB。

### 9.3 game-sdk（游戏作者视角）

```ts
registerGame({
  manifest,
  create(ctx: GameContext): GameInstance,
});

interface GameContext {
  storage: GameStorage;                    // 存档
  input:  { get(player: 1|2): Button[] };  // 当前帧输入（含远端）
  frame:  { now(): number; onTick(cb: (f:number)=>void): void };
  net:    { send(msg: SyncMessage): void; on(cb:(m:SyncMessage)=>void): void; isMultiplayer(): boolean };
  profile: 'host' | 'player' | 'controller' | 'solo';
}

interface GameInstance {
  tick(frame: number): void;   // 确定性逻辑
  render(): void;
  serialize(): Uint8Array;     // 预留：resync 快照
  destroy(): void;
}
```

游戏作者**只需**实现 `GameInstance` + 提供 manifest，不接触网络/存储/平台内部。

## 10. Nearby / Hotspot 引导（设计文档 §9–§11）

不依赖读取 Wi-Fi 信息，采用**能力探测 + 连接尝试**：

```text
加入房间 → 尝试 WebRTC 直连
   ├─ 连通且为本地候选 → 显示「已通过局域网连接」
   ├─ 连通但走公网     → 正常游玩
   └─ 超时失败(10s)    → 展示热点引导卡：
        1. 房主打开个人热点
        2. 玩家连接该热点
        3. 重新扫码/刷新 → 重试直连
```

浏览器无法代开系统热点，因此此步骤只能是**引导文案**（设计文档 §11 已明确）。

## 11. 扩展性设计

| 未来需求 | 现在预留的接缝 | 是否需改已有代码 |
|---|---|---|
| 新游戏 | 加 `games/<id>/`：manifest + entry + SDK 调用 | 否 |
| 新输入设备（如方向盘） | 实现 `InputSource` | 否 |
| 新传输（DO+WS 信令、TURN Relay、专用 LAN 协议） | 实现 `SignalingChannel` / `Transport` | 否 |
| 同步升级到 rollback / 确定性哈希校验 | 实现 `SyncStrategy`，协议已留 `hash`/`state` 消息 | 仅新增实现 |
| 3+ 人联机 | `players` 表与信令已按 room 多行建模；改拓扑策略与 manifest | 是（拓扑层） |
| 模拟器（EmulatorJS） | `GameRuntime` 与 HTML5 游戏同构，`type:"emulator"` 字段已留 | 否 |
| PWA / 离线 | 静态资源与游戏构建分离，可直接挂 Service Worker | 否 |
| Host Migration | 第一版明确不做（设计文档 §46）；`host_id` 可更新 | 是（后期） |

## 12. 里程碑

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **M0** | `protocol` + Worker 房间 CRUD/心跳/Token + D1 迁移 | `curl` 可建房、进房、心跳、关房 |
| **M1** | `game-sdk` + `storage` + `input` + `Loopback` + Snake 单机 | 无网络可玩 Snake、可存读档、手柄可用 |
| **M2** | 轮询信令 + WebRTC + QR + `player`/`controller` 双 profile | 两台设备扫码联机，手机作手柄、画面双端同步 |
| **M3** | 断线重连、HOST_LOST、热点引导、状态哈希校验 | 拔网/关页场景有明确 UI 反馈并可恢复 |
| **M4**（第二阶段） | EmulatorJS、PWA/离线、LAN 引导优化、多人>2 | 按设计文档 §44 |

每个里程碑结束跑一次：`pnpm typecheck && pnpm lint && pnpm test`。

## 13. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| JS 不确定性（`Math.random`/浮点）导致双端状态漂移 | 联机画面不一致 | Snake 强制种子化 PRNG + 定点运算；预留 hash 校验与快照 resync |
| WebRTC 对称 NAT 打洞失败 | 无法联机 | 明确失败提示 + 热点引导；TURN 列为 O1 |
| D1 免费额度（100k 写/天、5M 读/天）被轮询吃掉 | 信令失败 | 仅握手期轮询、1s 间隔、握手后停止、每次轮询顺带清理旧信号 |
| iOS Safari Gamepad/蓝牙手柄兼容性 | 手柄不可用 | M1 先以键盘+触屏为基线，Gamepad 作渐进增强 |
| 输入 `pressed=false` 丢包 | 按键卡死 | 每 500ms 全量按键快照自愈 |
| 免费版 Workers CPU 10ms/请求 | 轮询端点实现过重 | 端点只做索引查询与 JSON 组装，避免在 Worker 内做计算 |
